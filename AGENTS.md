# Zenith : guide pour les agents

> **Règle n° 1 : on travaille directement sur `main`.** Jamais de branche de travail ni de pull request, même si l'environnement en demande une : commit, push sur `main`, la CI compile et publie la release. Voir « Conventions ».

Lis ce fichier en entier avant de toucher au projet. Le README décrit le projet pour les humains ; ici, ce sont les règles, les décisions déjà prises et les pièges déjà rencontrés.

## Vision (à garder en tête à chaque modification)

- **Un Coyote gratuit, natif et minimaliste.** L'app doit être la plus simple et la plus rapide possible : un écran, une vitesse, une limite, la prochaine alerte. Chaque ajout doit justifier sa place à l'écran.
- **N'annoncer que ce qui est sur la route suivie.** Un radar sur une route parallèle, une bretelle qu'on ne prend pas ou une autre route « devant à vol d'oiseau » ne doit jamais être annoncé ni affiché comme « prochain ». Mieux vaut ne rien afficher qu'une information fausse ; mais un radar réel ne doit jamais être raté (en cas de doute sur la route, on alerte).
- **Des alertes à la Coyote** : sons forts et progressifs (bips qui s'accélèrent à l'approche quand on est trop vite), voix courte en français, ça marche écran éteint et Waze/Maps devant.
- **Le maximum de données gratuites, rassemblées par nos scripts.** La CI récupère tout ce qui est gratuit (liste officielle data.gouv, carte officielle Sécurité routière, OSM, Lufop avec la clé de l'auteur, et toute nouvelle source gratuite) et le fusionne dans de simples fichiers de la release `data`. L'app les télécharge régulièrement. Pas de serveur : la base grossit et se met à jour toute seule, jour après jour.
- **Dépôt public assumé** : la CI GitHub est gratuite et illimitée, il n'y a aucun intérêt à fermer le code.

## Ce qu'est Zenith

Application Android **minimaliste** d'alertes de conduite : vitesse, limitation, radars (positions exactes, façon Coyote), contrôles, tronçons. **Pas d'itinéraire, pas de navigation** : seulement une petite carte inclinée en haut de l'écran de conduite pour se situer (point bleu, route suivie en surbrillance, radars en mini-panneaux), qui se fond dans le fond noir. Elle tourne en fond, en complément de Waze ou Google Maps : un service de premier plan qui alerte par sons et voix même écran éteint.

Usage personnel de l'auteur, pas grand public. Interface et textes en français.

## Décisions prises (ne pas remettre en cause sans demande explicite)

- **Android natif Kotlin uniquement.** Pas d'iOS, pas de PWA, pas de Flutter. Google Play Services seulement pour la détection de conduite (`play-services-location`), facultative : sans eux, tout le reste marche.
- **Rien de payant** (règle de l'auteur) : ni compte développeur Google Play (25 $), ni service ou matériel payant. Une solution qui coûte de l'argent est écartée d'office.
- **Aucun serveur, aucune base de données hébergée.** GitHub Actions fabrique les données, publiées comme fichiers de la release `data`. L'app les télécharge et les met en cache. Supabase, Firebase, Cloudflare D1, VPS : écartés.
- **Dépôt public** (Actions gratuites et illimitées). Rien de secret dans le code : clés en secrets GitHub uniquement.
- **Radars en position exacte**, toutes sources activées par défaut, le plus de données possible sur la France.
- **Pas d'écran Android Auto** (décision de l'auteur, 28/10/2026, après essai) : une appli Car App Library n'apparaît dans Android Auto que si elle vient du Play Store, et le compte développeur est payant ; le code (écran complet par écran virtuel, alertes par-dessus Waze) a été retiré pour alléger l'app. Dans la voiture, Zenith passe par le son (Bluetooth ou Android Auto) : bips et voix sur les haut-parleurs, Waze ou Maps à l'écran. Au-dessus de Waze/Maps sur le téléphone : picture-in-picture, pas de bulle `SYSTEM_ALERT_WINDOW`.
- **Sons originaux synthétisés** (`Tones.kt`), jamais ceux de Coyote (protégés).

## Architecture

```
core/      Kotlin pur (JVM), testé : géo, Kalman, map-matching HMM, moteur d'alertes, règles FR,
           lecture des packs, GPX, DrivingSession (pipeline déterministe : replay = direct).
app/       Android Compose : DriveService (GPS 1 Hz, premier plan), DriveData (téléchargement/cache),
           DriveScreen, DriveMap (MapLibre), Onboarding (autorisations expliquées), Speaker (TTS FR),
           Tones, TripRecorder (GPX), Updater (auto-mise à jour).
           RoadHorizon : radars accrochés aux routes, chemin le plus probable, routes atteignables.
pipeline/  Python : build_roads.py (tuiles de limitations, zones bâties), build_radars.py (osm | merge | check),
           harvest_lufop.py (base Lufop qui grossit chaque jour), lufop_db.sh (base chiffrée).
.github/workflows/
  release.yml    push sur main touchant l'app → tests + APK signé + release vX (latest)
  build-apk.yml  lancement manuel → tests + APK debug (pour compiler une branche avant de la fusionner dans main)
  data.yml       lundi → extrait OSM France → tuiles + osm_radars.json + radars.json
  radars.yml     chaîne qui se relance seule toutes les 3 à 5 h (+ 6 crons jamais déclenchés) → récolte Lufop (≤150 requêtes
                 sur 24 h glissantes) + fusion → radars.json, official.json, lufop.json.enc
```
data.yml et radars.yml partagent le groupe de concurrence `data-release` (ils publient les mêmes fichiers).

### Release `data` (la « base de données »)

| Fichier | Produit par | Contenu |
|---|---|---|
| `radars.json` | data.yml, radars.yml | Fusion officiel (data.gouv + carte Sécurité routière) + OSM + Lufop, lue par l'app ; `zones` = itinéraires de contrôle |
| `official.json` | data.yml, radars.yml | Dernière copie valide des deux sources officielles et cache des détails de la carte (30 j) : si une source tombe, la fusion reprend sa copie |
| `osm_radars.json` | data.yml | Radars et relations `enforcement` OSM (sens, tronçons) |
| `lufop.json.enc` | radars.yml | Notre base Lufop **chiffrée** (AES-256, secret `LUFOP_DB_KEY`) : zones du quadrillage + radars vus (`first`, `seen`, `missing`) |
| `roads_<i>_<j>.json.gz` | data.yml | Tuiles 0,5° (`i = floor(lat*2)`, `j = floor(lon*2)`) de segments routiers avec limitation |
| `manifest.json` | data.yml | Liste et tailles des tuiles |

La release `data` est **prerelease et jamais latest** : sinon `releases/latest/download/zenith.apk` casse.

Format d'un segment de tuile : `[id, from, to, oneway, fwd, bwd, src, classe, nom, [lat, lon, ...]]` avec `src` 0 = explicite, 1 = implicite (`FR:urban`…), 2 = déduit de la classe, 3 = défaut du lieu (route sans aucune limite : 50 en zone bâtie, 80 hors zone sur double sens ; `LimitSource.AREA`, affichée en anneau gris, jamais dite ni prêtée à un radar).

Format d'une zone de `radars.json` : `{"id": "I_01_001", "kind": "ITINERARY", "pts": [lat, lon, ...]}` (itinéraire de contrôle-leurres de la carte officielle : un radar autonome tourne entre plusieurs cabines). Une fin de tronçon (`SECTION_END`) qui porte `len` n'a pas de début connu : l'app le place sur la route. Les indices de classe sont dans `pipeline/build_roads.py` (`CLASSES`) et `core/DataPacks.kt` : **les deux listes doivent rester identiques.**

## Commandes

```bash

./gradlew :app:assembleDebug               # nécessite le SDK Android (voir plus bas)
./gradlew :core:replay --args="trajet.gpx radars.json tuiles/"   # rejoue un trajet partagé depuis l'app

python pipeline/build_radars.py merge out/osm_radars.json out/lufop.json out/radars.json out/official.json   # lufop.json peut être "-"
LUFOP_API_KEY=... python pipeline/harvest_lufop.py out/lufop.json 150 [all]   # 150 sur 24 h glissantes ; all = tout le reste d'un coup
GH_REPO=LightZirconite/zenith LUFOP_DB_KEY=$(cat ~/.zenith/lufop-db.key) pipeline/lufop_db.sh fetch out/lufop.json
```

Tester le pipeline en local sur un petit extrait : `https://download.geofabrik.de/europe/france/corse-latest.osm.pbf` (35 Mo, environ 20 s). `pip install osmium` (pyosmium) n'est nécessaire que pour `build_roads.py` et l'étape `osm`. Sans accès à Geofabrik, un petit fichier `.osm` XML écrit à la main se lit pareil (ids triés : nœuds, puis chemins par id croissant).

## App : carte, autorisations, mises à jour

- **Carte** (`DriveMap.kt`) : MapLibre Android, tuiles vectorielles OpenFreeMap (gratuites, sans clé), style `dark` retouché (fond noir pour le fondu). Caméra détaillée ci-dessous. Toute erreur de carte laisse une boîte noire : la carte ne doit jamais faire planter l'app (une app qui plante au démarrage ne peut plus se mettre à jour). Attribution OSM/OpenFreeMap affichée en petit, obligatoire.
- **Caméra de la carte** : voiture à 45 % de la hauteur de la carte (le compteur couvre la partie fondue en dessous), vue assez haute (40° environ) pour voir loin devant ; dézoome avec la vitesse et, au besoin, pour cadrer le prochain radar de la route (jusqu'à 4 km), zoom lissé. On peut glisser/pincer la carte pour regarder ailleurs : elle se recadre seule 5 s après la fin du geste (élan compris, jamais pendant), ou tout de suite d'un appui sur la carte. Flèche de position posée à plat sur la route.
- **Attribution OpenFreeMap / OpenStreetMap** : sur l'écran d'accueil (pas sur la carte, à la demande de l'auteur). Ne pas la supprimer.
- **Picture-in-picture** (`PipScreen.kt`) : pendant une conduite, quitter Zenith (pour Waze, Maps…) l'ouvre en petite fenêtre, Zenith en miniature : carte en fond sur toute la fenêtre (assombrie, plus sombre vers le bas), pastille du prochain radar en haut, grosse vitesse et panneau de limite en bas, cadre rouge qui pulse si trop vite près d'un radar. Tailles proportionnelles à la fenêtre. La carte ne suit que start/stop du cycle de vie : en PiP l'activité est en pause mais visible, une MapView en pause se figerait. Auto sur Android 12+, `onUserLeaveHint` avant. Raccourcis « Ouvrir Waze / Maps » pendant la conduite (`<queries>` dans le manifeste). Conduite finie pendant le PiP (garé, voiture partie, démo terminée) : la fenêtre se ferme (`finishAndRemoveTask`) au lieu de rester figée sur la dernière vitesse. **Taille** : Android la déduit de la forme seule (aucune API de taille) ; la fenêtre carrée était jugée énorme par l'auteur, donc par défaut un bandeau 16:9, moins haut, et le réglage « Petite fenêtre carrée » pour la grande. La mise en page s'adapte (unités = 1 % du petit côté).
- **Notification** : solide tant que « Arrêter » n'est pas touché : balayée (permis depuis Android 14), elle revient aussitôt (`setDeleteIntent` → `ACTION_RESHOW`) et elle est reposée toutes les 30 s. Vitesse et limite en titre, prochain radar en texte ; sur Android 16, puce de vitesse dans la barre d'état (`setRequestPromotedOngoing`, `POST_PROMOTED_NOTIFICATIONS`, ne pas la coloriser sinon Android refuse la promotion).
- **Geste sur la carte Musique** (`MediaBar.kt`, demande de l'auteur) : glisser vers la gauche = titre suivant, vers la droite = précédent. Jamais par accident (demande de l'auteur) : il faut un glissement long (72 dp de bande, environ 120 dp de doigt, avec résistance), nettement horizontal (dérive verticale < moitié du trajet), une vibration et « Suivant › / ‹ Précédent » signalent le seuil, revenir avant de lâcher annule, et un second changement attend 1 s.
- **Décollage** (`Warp.kt`, `Globe.kt`, demande de l'auteur : immersif, façon saut dans l'espace) : à l'accueil, un ciel d'étoiles dérive derrière le logo. « Démarrer » : le logo file vers le spectateur, un tube d'étoiles se forme autour de lui (anneaux de lumière sur ses parois) et accélère progressivement (plus vite au fil des secondes et des satellites captés) ; au bout du tunnel, **la Terre** (`Globe`) : continents en points lumineux (masque terre/mer de 2,5° embarqué en texte, 6 points par caractère), océan sombre éclairé d'en haut à gauche, halo d'atmosphère, lumières de villes côté nuit ; les satellites en vue tournent sur trois orbites inclinées (point lumineux, traînée), verts une fois utilisés et reliés par un faisceau (impulsions de données) à une balise sur la France ; la Terre ralentit à chaque satellite et tourne la France vers le spectateur. (L'ancien cadran à graduations et les satellites dessinés en rectangles ont été retirés : jugés « pas incroyables » par l'auteur.) Sous le globe, en texte seul : « Contact des satellites… » → « Triangulation · 2 sur 4 » → « Position verrouillée » (le texte roule), quatre voyants qui s'allument en rebondissant, une note douce par satellite (mi, sol#, si, puis accord de mi : sinus à attaque douce, pas de clochette). La barre d'état (heure, batterie) se range pendant tout le vol (`ImmersiveBars`), sa place gardée (rien ne saute). Au premier point avec vitesse fiable (ou 15 s après un point sans vitesse ; vol d'au moins 3,5 s), saut de 1,8 s : traînées d'étoiles filantes, la Terre fonce sur le spectateur jusqu'à remplir l'écran (plongée dans les points), éclair blanc ; la scène (carte et Canvas, construits et chargés dès « Démarrer ») s'ouvre en **portail** circulaire depuis le cœur du tunnel (`HEART_Y`, 42 % de la hauteur), en dézoomant (1,35 → 1), avec une onde de choc ; puis la vitesse arrive en zoom, enfin la musique et les raccourcis glissent en place l'un après l'autre. Démo : satellites simulés (un toutes les 0,65 s). Ouvert en pleine conduite : directement la carte. Sons synthétisés (`WarpSound`, aucun fichier) : moteurs (2,2 s), bourdonnement en boucle qui s'éteint en fondu, ruée puis boum rond et grave avec un accord chaud qui s'éteint lentement (pas de clochette, demande de l'auteur).
- **Musique pendant le décollage** (demande de l'auteur) : à « Démarrer », la musique baisse (baisse d'Android, environ 0,5 s) puis se met en pause (`TRANSIENT` 0,65 s après) ; au boum de l'arrivée elle reprend, encore baissée sous l'accord, puis remonte en douceur à son volume 1,6 s plus tard. Vol interrompu (« Arrêter »), écran éteint ou app quittée pendant le vol : elle revient aussitôt ; recherche GPS de plus de 12 s : elle revient sans attendre le saut. Musique déjà en pause avant « Démarrer » : elle reste en pause (l'auteur hésitait à la lancer ; un lecteur qu'on démarre prend lui-même le focus, Android ne permet donc pas de le faire monter en fondu). `WarpSound` a son propre `AudioDucker` (contexte de l'activité, donc client de focus distinct de celui du service).
- **Retour dans les étoiles** (à l'arrêt d'une conduite) : la scène se referme en portail vers le cœur en reculant (1 → 0,75) avec une onde qui se resserre, les étoiles reviennent en trombe puis ralentissent jusqu'à la dérive de l'accueil (sortie d'hyperespace, lueur au cœur), l'accueil arrive du lointain, ses boutons remontent en place.
- **Carte et Canvas** : la carte fait 80 % de la hauteur ; le fond musical couvre tout l'écran mais son masque (`BackdropMask`, en fractions de l'écran) ne le montre qu'à partir de 20 %, et le fondu reste au même endroit (demande de l'auteur) : seule, la carte se fond dans le noir à 62 % comme avant (`MapAlone`) ; avec musique, le Canvas est **sous** la carte, qui s'efface par un masque d'opacité (`verticalFade`, `MapOverCanvas` : moitié-moitié vers le milieu de l'écran, puis une longue traîne pâle où l'on devine encore des routes sur le Canvas).
- **Mode musique selon la vitesse** (`core/Cockpit.kt`, demande de l'auteur) : lent ou arrêté, le Canvas monte (la carte ne garde que le haut, `MapInMusicMode`, Canvas plus lumineux), progressivement : entier sous 8 km/h, plus rien dès 40 km/h, en courbe douce entre les deux, animé lentement. Une alerte ou un tronçon rend la carte aussitôt. Toucher la pochette ou le titre inverse ce qui est montré et garde ce choix jusqu'à ce que la vitesse donne la même chose (grand demandé sur la route : rendu à la vitesse une fois arrêté ; petit demandé à un feu : rendu une fois repartis à 40) ; et au plus 3 min sans nouvel appui (`Cockpit.CHOICE_MS`, demande de l'auteur : ensuite le mode progressif reprend, par l'animation habituelle) ; le choix vit dans `DriveState.musicChoice` avec son heure, remis à zéro à chaque conduite. Même règle dans la petite fenêtre : lent, la carte y laisse plus voir le Canvas (`MeltStopsSlow`). En mode musique, le haut du Canvas garde un long fondu sous la carte (`BackdropMaskFocus` : l'auteur trouvait le bord trop net). Appui long : ouvre le lecteur.
- **Boutons selon la vitesse** (`Cockpit.cruising`) : dès 30 km/h, « Arrêter » devient plus bas et plus discret et les raccourcis Waze / Maps se replient ; ils reviennent sous 12 km/h (écart voulu : pas de clignotement en ville).
- **Vidéos (YouTube)** (`core/Music.kt`, `VideoTitle`) : pour une vidéo classique regardée sur YouTube (la musique passe plutôt par YouTube Music, déjà propre) : « Artiste - Titre (Clip officiel) » par « ArtisteVEVO » s'affiche « Titre » par « Artiste » (balises retirées, suffixes VEVO / Topic / Officiel des chaînes) ; miniature en 16:9 ; boutons « −10 » / « +10 » secondes à la place de précédent / suivant (`NowPlaying.seekBy`), le glissement change toujours de vidéo.
- **Trop vite près d'un radar** : les bords de tout l'écran pulsent en rouge (`DangerGlow`), en plus de la carte d'alerte.
- **Radar passé** (`RadarPassWave`) : une bande de lumière balaie l'écran de haut en bas, comme sous un portique, verte (rouge si le radar aurait flashé) ; pareil en fin de tronçon.
- **Accueil** : le nombre de radars défile en comptant à l'ouverture ; le bouton « Démarrer » émet de temps en temps une onde lumineuse.
- **Style** (`Style.kt`, demande de l'auteur : immersif, fondu, premium, façon iOS) : surfaces en verre (`Modifier.glass` : verre translucide + liseré clair de 0,5 dp), boutons qui s'enfoncent sous le doigt et rebondissent (`Modifier.tap`, indication `PressScale` au lieu de l'onde Material ; à poser avant le `glass` pour que toute la surface bouge). Animations à ressort : carte d'alerte qui monte et grandit, panneau de limite qui « saute » quand la limite change, passage accueil ↔ compteur en zoom doux, carte qui atterrit sous l'éclair du décollage, interrupteurs des réglages. Chiffres de vitesse à chasse fixe (`tnum`) : le nombre ne bouge pas en changeant. Le verre est éclairé par le haut (`GlassSheen`) ; une carte d'alerte ou de tronçon qui arrive est traversée une fois par un reflet (`Modifier.sheen`) ; un nouveau panneau de limite envoie un anneau ; les puces d'état arrivent en rebondissant ; le mot « Démarrer » / « Arrêter » roule comme un interrupteur. - **Sons** (`AudioDucker.kt`, `Speaker.kt`, `Tones.kt`, demande de l'auteur du 28/10/2026) : les bips **ne mettent jamais la musique en pause**, ils la baissent seulement (`TRANSIENT_MAY_DUCK` : Android la descend à environ 20 % et la remonte, en fondu dans les deux sens) ; entre deux bips de danger (jusqu'à 2 s d'écart) la musique reste basse (2,6 s de maintien) au lieu de pomper. La voix baisse aussi la musique en fondu, par défaut ; le réglage « Musique en pause pendant la voix » (désactivé par défaut, clé `voice_pause` : l'ancienne `pause_music` est volontairement oubliée) la baisse d'abord puis la met en pause 0,65 s plus tard (`TRANSIENT`), jamais de coupure nette ; la voix finie, si des bips continuent, elle rejoue baissée (rendre le focus puis le reprendre en baisse : un lecteur en pause ne reprend qu'au retour du focus). Un seul propriétaire du focus pour les tons et la voix (sinon l'un rend le focus de l'autre), musique rendue 1,5 s après le dernier son. Alerte urgente (ralentis, limite, flash) : `QUEUE_FLUSH`, les annonces plus vieilles en attente sautent. Bips de danger muets pendant la voix. Sortie Bluetooth (A2DP, SCO, BLE) : 300 ms de silence avant un son, sinon la voiture avale le début.
- **Pluie automatique** (`core/Weather.kt`, réglage activé par défaut) : pendant la conduite, Open-Meteo (gratuit, sans clé) toutes les 10 min à la position arrondie à 0,1° ; pluie au premier relevé humide (précipitations ≥ 0,1 mm ou code WMO de pluie, neige, averse, orage), fin après deux relevés secs. Carillon + voix au changement. Aucune puce ni commande manuelle (demande de l'auteur : c'est automatique, rien à toucher) ; à l'arrêt, retour au sec.
- **Musique** : voir la section « Musique : carte et Canvas Spotify ». Sessions média d'Android, **aucune API Spotify, aucun compte, aucun serveur** (demande de l'auteur) ; accès aux notifications obligatoire. Le Canvas tourne en boucle libre : pas de synchro avec Spotify (décision de l'auteur, impossible d'être exactement calé) (`MediaListener`, vide : il ne lit aucune notification).
- **Démarrage en roulant** (`Motion.kt`, réglage activé par défaut) : transitions `IN_VEHICLE` de Play Services (presque sans batterie, app fermée). Entrée → `DriveService.startMotion` ; sortie → arrêt si la conduite vient de là et roule à moins de 10 km/h, sinon au premier fix lent des 3 min suivantes (la sortie arrive souvent en entrant dans l'allée) ; ensuite `ParkDetector`. Faux départ (Play Services se trompe parfois à la maison) : une conduite démarrée ainsi qui ne dépasse jamais 20 km/h s'arrête après 5 min. Il faut « Activité physique » et la position « Toujours » (un service de premier plan lancé depuis l'arrière-plan n'a pas le GPS sans elle) ; demandées depuis la carte « Démarrage en roulant » des réglages. Si Android refuse le démarrage : notification « En voiture ? · touche pour démarrer ». Inscription refaite à chaque lancement, au démarrage du téléphone et après mise à jour (`MotionBootReceiver`).
- **Arrêt automatique** (`core/ParkDetector.kt`, réglage « Arrêt automatique », activé par défaut) : une conduite lancée à la main s'arrête seule quand la voiture reste dans 300 m pendant 10 min, quand on ne dépasse plus 8 km/h pendant 15 min sans charger le téléphone (à pied), ou sans aucun fix GPS pendant 10 min (30 min si le dernier fix était rapide : tunnel). Jamais sur autoroute ou voie rapide (bouchon). Une conduite lancée par la voiture s'arrête à sa déconnexion, pas par ce détecteur (sinon : arrêt en attendant dans la voiture, puis aucun redémarrage puisque le Bluetooth reste connecté).
- **Fil de conduite** : `DriveService` traite chaque fix sur son propre fil (`zenith-drive`, un fix après l'autre) : l'horizon routier et l'écriture du GPX n'encombrent plus l'interface. Une étape qui lève une exception est journalisée et sautée. Les tuiles autour de la dernière position connue se chargent dès le démarrage.
- **Réglages** (`SettingsScreen.kt`, `UserSettings.kt` ; ne pas nommer l'objet `Settings`, conflit avec `android.provider.Settings`) : rangés en sections façon iOS (Alertes ; En voiture ; Musique et petite fenêtre ; Application : mises à jour, dernier trajet), les plus utiles en haut ; jeune permis, pluie automatique, voix ou bips seuls, voitures pour le démarrage auto, partage du dernier trajet GPX (FileProvider). Le profil est appliqué en direct à `DrivingSession.profile`.
- **Démarrage auto en voiture** (`CarLink.kt`, Android 13+) : **plusieurs voitures** possibles (demande de l'auteur), chacune choisie par l'écran compagnon d'Android (`CompanionDeviceManager`, sans autorisation Bluetooth), listées dans les réglages (« Ajouter une voiture », « Retirer » par voiture ; `SettingsState.cars`, JSON dans la clé `cars`, l'ancienne voiture unique `car_id` / `car_name` reprise une fois) ; `CarPresenceService` reçoit connexion et déconnexion de chacune. Si Android refuse le service de premier plan depuis l'arrière-plan, une notification « Voiture connectée · touche pour démarrer » prend le relais. À la déconnexion, seule une conduite démarrée par la voiture s'arrête.
- **Tunnels** : sans fix depuis 2,5 s, `DrivingSession.coast` avance la voiture le long de la route suivie à sa dernière vitesse (60 s max), puce « Tunnel · position estimée ».
- **Trajets GPX** : les 10 derniers sont gardés, les plus vieux supprimés. Écrits par ajouts toutes les 30 s (nouveaux points écrits à la place de la fin du fichier, fin réécrite après) : toujours un GPX complet, jamais réécrit en entier.
- **Voiture qui roule vraiment** (`core/MotionGate.kt`, bug réel : « radar passage à niveau » annoncé à la maison) : rien n'est annoncé ni affiché comme prochain tant que la position n'a pas vraiment voyagé (distance nette ≥ 20 m et ≥ 2 × la précision annoncée, vitesse moyenne et Doppler ≥ 9 km/h, précision ≤ 30 m, 3 fixes de suite). Arrêté (feu, bouchon, sous 5,4 km/h) : rien de nouveau, les radars suivis restent figés (le cap et la route sont du bruit à l'arrêt). Immobile 60 s dans 20 m : garé, plus rien d'affiché jusqu'au départ, puis les radars déjà annoncés reviennent sans nouvelle annonce.
- **Données sur le téléphone** (`DriveData`) : `radars.json` rafraîchi s'il a plus de 4 h ; une tuile dont la taille diffère du manifeste est re-téléchargée (reconstruction hebdomadaire), l'ancienne sert hors ligne ; une tuile illisible est supprimée pour être reprise.
- **APK arm64-v8a seulement** (`abiFilters`) : MapLibre embarque du code natif, l'APK universel serait 3 fois plus gros.
- **Premier lancement** (`Onboarding.kt`) : une barre se remplit au fil des autorisations, chaque étape accordée s'allume (coche qui rebondit, anneau de lumière), le bouton roule de « encore 3 » à « C'est parti » qui pulse en vert. Chaque autorisation est expliquée avant la fenêtre d'Android (position obligatoire ; notifications, installation d'applications inconnues, batterie sans restriction, démarrage en roulant, musique conseillés). Après deux refus, Android n'affiche plus sa fenêtre : le bouton ouvre alors les réglages.
- **Toutes les autorisations sont obligatoires** (demande de l'auteur) : l'écran de bienvenue revient dès qu'une manque (nouvelle fonction ou autorisation retirée), jamais pendant une conduite, et « C'est parti » ne s'active qu'une fois tout accordé (`Permissions.missing`). Le démarrage en roulant ne compte que si les services Google sont là et le réglage actif. Toute nouvelle autorisation va dans cet écran, pas seulement dans les réglages.
- **Assistant d'autorisations** : un seul gros bouton « Continuer · encore N » ouvre l'autorisation manquante suivante (position, notifications, batterie, installations, démarrage en roulant, musique) ; « Activité physique » accordée enchaîne seule sur la position « Toujours ».
- **Accès aux notifications, Android 13+** (appli installée hors store) : le bouton suit trois étapes (`media_step`) : « Activer » (Android bloque, mais c'est ce qui fait apparaître le déblocage), « Débloquer » (infos de l'appli → ⋮ → « Autoriser les paramètres restreints », code), puis « Activer ». Ne pas tenter de contourner cette protection (par exemple en déclarant une autre source d'installation).
- **Mises à jour** (`Updater.kt`) : vérification à chaque retour au premier plan puis toutes les 2 min tant que l'app est devant (`repeatOnLifecycle(RESUMED)`, 1 min minimum entre deux ; avant, 30 puis 5 min empêchaient de voir une release sortie juste après et l'auteur devait forcer l'arrêt). État `Checking` visible ; le bouton « Rechercher maintenant » force la vérification quel que soit l'état (sauf téléchargement ou installation en cours) ; une release encore sans APK revient à `Idle`. Une installation sans réponse depuis 2 min ne bloque plus les vérifications. Carte « Mises à jour » dans les réglages (section Application) : état (à jour, téléchargement, erreur) et bouton « Rechercher maintenant ». À l'arrêt, installation dès le téléchargement fini. La demande de confirmation d'Android passe par l'état (`NeedsConfirmation`) et n'est ouverte que quand l'activité est au premier plan : lancée depuis le `BroadcastReceiver` en arrière-plan, Android la bloquait et la mise à jour restait figée. Après une première auto-mise à jour, Zenith devient l'installateur de l'app et Android 12+ installe les suivantes sans confirmation (`USER_ACTION_NOT_REQUIRED`). L'APK téléchargé est supprimé après l'installation.

## Musique : carte et Canvas Spotify

- **Carte Musique** (`MediaBar.kt`, `NowPlaying.kt`, logique pure dans `core/Music.kt`) : pour **tout lecteur** qui publie une session média (Spotify, YouTube, YouTube Music, Deezer…) : pochette, titre, artiste (ou chaîne), précédent / lecture-pause (disque blanc) / suivant, fine ligne de progression en bas (`PlaybackState.position` + `lastPositionUpdateTime` + `playbackSpeed`, durée `METADATA_KEY_DURATION`, redessinée 4 fois par seconde sans recomposition ; pas de ligne sans durée). Une touche sur la pochette ou le titre ouvre le lecteur (`sessionActivity`, sinon son lanceur). La carte elle-même est une fine bande de verre translucide (`Glass`), la même que toutes les puces, cartes et boutons de l'écran de conduite (demande de l'auteur : style verre, partout pareil). L'ambiance est à l'échelle de l'écran (`MusicBackdrop`, demande de l'auteur) : le Canvas Spotify, sinon la pochette floutée (copie de 24 px agrandie, plus `Modifier.blur` sur Android 12+), monte du bas sur 62 % de la hauteur ; elle passe sous la carte, qui s'y fond par un masque d'opacité (voir « Carte et Canvas »), assez sombre pour la vitesse. Pendant une alerte, elle s'efface encore : la carte et la vitesse restent les héros.
- **Quel lecteur suit la carte** (`core/Music.kt`, `PlayerChoice`, demande de l'auteur) : toutes les sessions sont suivies, pas seulement celle affichée ; ce qui joue gagne, une plateforme de musique d'abord (`PlayerChoice.MUSIC` : Spotify, Deezer, YouTube Music, Apple Music…) ; rien ne joue : la dernière plateforme de musique plutôt qu'une vidéo en pause ; à rang égal, la carte garde celle affichée (pas de clignotement). Une vidéo YouTube qui joue pendant que Spotify est en pause prend la carte, Spotify revient quand elle s'arrête.
- **Canvas pour tous les lecteurs** (demande de l'auteur : Deezer, YouTube Music, Apple Music dont le Canvas par album est jugé nul…) : hors Spotify et hors vidéo YouTube, `NowPlaying` remplit `canvasQuery` (titre, artiste, album, durée) et `CanvasFinder.search` demande au serveur d'AuraMusic (`/api/canvas?song=&title=&artist=&album=&durationMs=`, gratuit, sans compte) le titre Spotify correspondant et son Canvas ; la réponse est gardée sous la clé de recherche (casse et accents ignorés) et sous l'id Spotify, la vidéo se télécharge et se joue comme celle de Spotify. Couverture partielle (relevé du 28/10/2026 : « Djadja » trouvé, « Jefe » et « Blinding Lights » non) : sans Canvas, la pochette floutée reste.
- **Identifiant Spotify** : l'appli Spotify met `spotify:track:<id>` dans `METADATA_KEY_MEDIA_ID` (parfois `METADATA_KEY_MEDIA_URI`), relevé par plusieurs applis libres. Seule la session de `com.spotify.music` donne un id (`SpotifyTrack.idFromSession`) : le Canvas est réservé à Spotify. Les diffusions `com.spotify.music.metadatachanged` donnent aussi l'id, mais seulement si l'utilisateur active « Device Broadcast Status » : inutile.
- **Cœur** (titres likés) : actions personnalisées de la session Spotify, `ADD_TO_COLLECTION` tant que le titre n'est pas liké, `REMOVE_FROM_COLLECTION` ensuite (Spotify propose l'inverse de l'état). Envoyées par `sendCustomAction` : ni API Web Spotify ni compte (gardé à la demande de l'auteur pour cette raison). Affiché seulement si la carte fait au moins 340 dp de large (sinon le titre n'a plus de place).
- **Canvas** (`SpotifyCanvas.kt`, `CanvasVideo.kt`, `core/Canvas.kt`, réglage « Canvas Spotify », activé par défaut) : pas d'API officielle. On demande l'adresse de la vidéo à deux services gratuits et non officiels, sans compte ni clé, tenus par d'autres projets : le magasin de Canvas de Spicy Lyrics (`regional.canvasstore.slnode.spicylyrics.org/provider/canvaslist/<id>`, que l'appli Android Spicy Lyrics interroge aussi depuis le téléphone), puis, seulement s'il échoue, le serveur d'AuraMusic (`canvas.auramusic.site/api/canvas?trackId=<id>`, plus lent et parfois 15 s sans réponse). « Pas de Canvas » (environ un titre sur deux) est une vraie réponse, gardée un jour ; une vidéo trois jours ; si tout échoue, pause de 1 min qui double jusqu'à 30 min. User-Agent honnête (`Zenith (+github)`). Seul un MP4 HTTPS de `*.scdn.co` est accepté.
- **Vidéo** : MP4 H.264 1080×1920 de 3 à 8 s, sans son, environ 3,6 Mo. **Téléchargée une fois** dans `cache/canvas/<id>.mp4` (60 Mo au plus, les plus anciennes partent), puis jouée en local : une lecture en boucle depuis le réseau pourrait la retélécharger à chaque tour. `MediaPlayer` + `TextureView` (aucune dépendance), muet, en boucle, recadré au centre par matrice ; il ne joue que si la musique joue et que l'activité est démarrée (écran allumé, devant ou en PiP), et il est libéré avec le composable. Toute erreur (lecteur, fichier, réseau) est silencieuse : la vidéo est oubliée et la pochette reste.
- **Canvas en PiP** (`PipScreen.kt`) : la carte remplit toujours toute la fenêtre, voiture au milieu, dans les deux tailles (demande de l'auteur : la carte complète, le Canvas seulement en fond sans la déranger). Le Canvas remplit la fenêtre **derrière** la carte, qui reste entière en haut et devient à peine transparente vers le bas (opacité 1 → 0,92 → 0,68) : il la colore par transparence, sans jamais couvrir une route. Il n'apparaît qu'à sa première image, plus discret pendant une alerte. Un seul lecteur vidéo à la fois : passer en PiP retire l'écran de conduite (lecteur libéré) avant de créer celui de la fenêtre.
- **Pourquoi l'accès aux notifications** : `MediaSessionManager.getActiveSessions` exige `MEDIA_CONTENT_CONTROL` (`signature|privileged`, réservé au système) ou un `NotificationListenerService` activé. Se connecter au `MediaBrowserService` d'un lecteur : Spotify, YouTube Music et d'autres n'acceptent que des applis sur liste blanche (Android Auto, Waze…). SDK App Remote de Spotify : identifiant client, empreinte de l'APK, autorisation de l'utilisateur et AAR hors Maven, pour Spotify seul : écarté.

## Horizon électronique (`core/RoadHorizon.kt`)

- `RadarSnapper` rattache chaque radar aux chaussées à moins de 30 m. Toutes celles à moins de 10 m de la plus proche sont gardées (radar entre deux chaussées : alerte des deux côtés). Sans sens mesuré, une route à sens unique donne le sens. Sans route à 30 m, la seule route la plus proche jusqu'à 75 m (positions officielles sur le bas-côté : 9 sur 321 à Paris) plutôt que le cône en ligne droite.
- Une limite étiquetée pour un seul sens d'une route à double sens ne vaut pas pour l'autre (`RoadSegment.limitKmh`).
- `mostProbablePath` suit la route (même nom/`ref`, puis même classe, puis virage nettement le plus droit) et **s'arrête au premier embranchement ambigu**. Le « prochain radar » et la prochaine limite ne viennent que de ce chemin, distance par la route.
- `reachable` : Dijkstra sur toutes les branches jusqu'à 3,2 km, portée constante (sinon un radar suivi sortirait de la portée en ralentissant et serait annoncé deux fois). Un radar hors du chemin probable n'alerte qu'à 500 m (`branchAlertM`) : la bretelle n'alerte pas toute l'autoroute, mais prévient avant la sortie.
- Repli sûr : radar à plus de 30 m de toute route, ou pas de tuile chargée → ancienne logique du cône devant la voiture (le « prochain » est alors limité à 3 km).
- **Tronçon sans début** : une fin de tronçon avec `len` crée un début virtuel (`<id>>start`, type `SECTION_START`) placé sur le chemin probable `len` mètres avant la fin ; il est annoncé, affiché comme prochain, et son passage démarre la moyenne. Voiture déjà dans le tronçon (démarrage, tuile chargée tard) : « Tronçon en cours » avec ce qui reste (au moins 300 m). Seulement si le sens est connu (sens mesuré ou chaussée à sens unique) : sinon un tronçon s'afficherait dans l'autre sens.
- **Doublons** : un radar du même type à moins de 150 m d'un radar déjà annoncé (même caméra, deux sources) est suivi en silence, sauf si leurs sens mesurés diffèrent de plus de 25° (deux caméras d'un passage à niveau ou d'un carrefour : les deux sont annoncées).
- **Passé ou tourné avant** : un radar n'est « passé » (flash probable, vague) que si sa distance par la route était presque nulle quand elle a disparu (30 m ou deux fixes) ; sinon la voiture a tourné avant, sortie silencieuse. Une branche (hors chemin probable, ≤ 500 m) derrière la voiture n'est jamais annoncée (demi-tour par un rond-point). Tronçon : à l'arrêt le bruit GPS n'avance pas la distance ; un fix en retard est ignoré. Itinéraire de contrôle : pas d'entrée sans rouler.
- **Banc d'essai sur les vraies données** (`core/FieldAudit.kt`, `./gradlew :core:audit --args="radars.json dossier_des_tuiles [trajets] [graine]"`) : trajets de 6 km qui suivent la route comme un conducteur (au hasard aux vrais embranchements), bruit GPS, comparés au trajet réel : radars ratés, annonces hors route, « prochain » faux, faux flash. Relevé du 28/10/2026 après correctifs (600 trajets par tuile, Paris 97_4, Lyon 91_9, campagne 90_5 + 95_0) : 0 raté sur 101 radars, 0 annonce hors route au-delà de 500 m, 0 faux flash, « prochain » faux 0 % (Lyon, campagne) et 2 % (Paris, un radar). À relancer après tout changement de la logique d'alerte.
- Les caméras de tronçon ne donnent jamais « flash probable » au passage : seule la moyenne compte.
- **Itinéraires de contrôle** (`ControlZones.kt`) : la voiture doit rouler à moins de 40 m de la ligne et dans son axe (±35°, les deux sens) pendant 3 fixes pour y entrer, en sortir pendant 5 fixes en roulant (un arrêt ne compte pas). Pas de seconde annonce dans les 3 min (rond-point hors de la ligne).

## Pièges déjà rencontrés

- **« Prochain radar à 14 km » sur une autre route** : l'ancien moteur prenait le radar le plus proche à vol d'oiseau dans un cône de ±35° jusqu'à 15 km (à 14 km, le cône fait 16 km de large). Corrigé par l'horizon : ne jamais revenir à une recherche en ligne droite quand une route est reconnue.
- **« Limite 80 » répété** quand la vitesse oscille autour de limite + 3 : l'annonce attend 30 s, ou 10 s sous la limite.
- **Date des mobiles Lufop** : `update` doit passer dans `radars.json` (`at`, secondes epoch, heure de Paris) ; sans date, un mobile vieux d'une semaine serait annoncé comme en direct. `RadarPack` ne garde la date que pour les types mobiles.
- **Quota Lufop partagé** : la clé sert à la CI (150/jour) ; des requêtes depuis le téléphone (mobiles en direct) prendraient sur les mêmes 200/jour.
- **Android 12+** interdit de lancer un service de premier plan `location` depuis l'arrière-plan (démarrage auto au Bluetooth) : passer par `CompanionDeviceManager`.
- **Maven Central en 429** derrière certains proxys (conteneurs cloud) : un init script local `~/.gradle/init.d/mirror.gradle` qui **remplace** `mavenCentral()` par le miroir `https://maven-central.storage-download.googleapis.com/maven2/` suffit (`settingsEvaluated` : `repos.removeAll { it.name == "MavenRepo" }` puis le miroir **en premier** (`def m = repos.maven { url = ... }; repos.remove(m); repos.addFirst(m)`), pour `pluginManagement` et `dependencyResolutionManagement`). L'ajouter seulement à la fin ne suffit pas : le portail des plugins Gradle redirige les artefacts Kotlin vers Maven Central et Gradle s'arrête sur le 429. Ne pas l'ajouter au dépôt.
- **Vérifier la compilation de l'app sans SDK Android** (conteneur, licences du SDK jamais acceptées) : `./gradlew -I cp.gradle :app:printCp --no-configuration-cache` avec un init script qui écrit les fichiers de `releaseCompileClasspath` vus en `artifactType = android-classes-jar` (Gradle télécharge Compose sans SDK), plus le framework Android de Robolectric (`org.robolectric:android-all:17-robolectric-15733970` sur Maven Central), puis `K2JVMCompiler` du cache Gradle avec `-Xplugin=` le `kotlin-compose-compiler-plugin-embeddable` de la même version que Kotlin. Seules restent les erreurs de la classe `R` (générée par le build Android). Puis `build-apk.yml` sur la branche pour la vraie compilation.
- **Crons GitHub qui ne partent pas** : au 28/10/2026, aucune exécution `schedule` pendant 27 h dans tout le dépôt (ni `radars.yml`, ni `data.yml`) ; le premier est parti à 19 h 03 UTC, plus d'une heure après son créneau. On ne compte donc pas dessus. Le job `next` reste « en cours » pendant ses 3 à 5 h de pause : c'est normal (l'auteur l'a pris pour un bug ; l'étape le dit maintenant dans son nom). Plusieurs `next` peuvent dormir en même temps (un par passage) : au réveil, chacun s'arrête s'il existe un passage plus récent, il n'en reste qu'une chaîne. `radars.yml` se relance donc lui-même : un job `next`, hors du groupe `data-release` (sa pause bloquerait `data.yml`), attend 3 à 5 h puis lance `radars.yml` (`workflow_dispatch`, `chained=true` : part aléatoire du quota, pas tout) ; il s'arrête si une exécution plus récente existe (les chaînes ne se multiplient pas). Un push de `radars.yml` sur `main` ou un lancement manuel relance la chaîne si elle casse. Ce même job lance `data.yml` quand le `manifest.json` de la release a plus de 7 jours (son cron hebdomadaire ne partait pas non plus) et qu'aucun `data.yml` ne tourne : tout le circuit des données est autonome. Les deux se raniment l'un l'autre : `data.yml` relance la chaîne `radars` si aucun passage ne tourne ; l'appel qui relance la chaîne est réessayé 5 fois. Les crons gardés dans les deux fichiers ne servent que s'ils se mettent un jour à partir. But de l'auteur : les radars se mettent à jour seuls, indéfiniment, sans personne derrière ; seule l'app demande des pushes (nouvelles fonctions, Android). Le quota glissant garantit toujours ≤ 150 sur 24 h.
- **Conteneur cloud** : data.gouv.fr, Geofabrik et Open-Meteo y sont injoignables ; l'API de la carte Sécurité routière et les releases GitHub répondent. Tester `merge` en remplaçant `official()` par une fonction qui lève : la copie `official.json` prend le relais.

- **Android Auto refuse les applis hors Play Store** : une appli Car App Library (type `template`) n'y apparaît que si elle vient d'une source de confiance (Play Store, partage interne, test interne, tous liés au compte développeur payant). « Sources inconnues » des paramètres développeur ne couvre que les applis média, messagerie et « parked » (doc Google `training/cars/testing`). Voies gratuites étudiées : KingInstaller (installation enregistrée au nom du Play Store, fiable jusqu'à Android 13, souvent bloquée dès 15, plus de mise à jour automatique), applis « parked » (seulement voiture garée), root ou boîtier AAWireless en mode développeur. Ne pas reconstruire d'écran Android Auto sans nouvelle demande de l'auteur. Si un jour : seule la catégorie navigation donne une surface, rendue par une `Presentation` sur un écran virtuel privé avec `ViewTreeLifecycleOwner` et `ViewTreeSavedStateRegistryOwner` (voir l'historique git, commit `50e541b`).
- **AGP 9** : Kotlin intégré, ne **pas** appliquer `org.jetbrains.kotlin.android` ; `kotlin { compilerOptions { } }` au lieu de `kotlinOptions`.
- **compileSdk 37** obligatoire avec les AndroidX actuels (targetSdk 36).
- `x in concurrentHashMap` appelle `containsValue` : utiliser `containsKey` (le compilateur bloque, heureusement).
- **Overpass est trop instable** pour la CI (502/504 sur tous les miroirs, plus de 40 s par petite tuile) et exige un User-Agent. On lit l'extrait OSM Geofabrik à la place.
- **Waze live-map** (`/live-map/api/georss`) répond 403 sans navigateur : non branché.
- **Doc Lufop** (api.lufop.net) derrière une vérification anti-bot Cloudflare : ne pas la contourner (ni faux User-Agent, ni résolution de défi).
- **Map-matching aux bretelles** : sans hystérésis, la limite affichée clignote (130 → 70) à chaque sortie d'autoroute. L'hystérésis suit aussi la continuation du segment courant, avec une pénalité de changement de classe, et elle est désactivée pendant les 5 premiers points.
- **Vitesse à l'arrêt** : le GPS donne 1 à 6 km/h de bruit. `SpeedStabilizer` affiche 0 sous 5 km/h (sortie sous 2,5), n'affiche rien tant que la précision dépasse 30 m, et privilégie la vitesse Doppler.
- **Paramètres restreints** (Android 13+) : une app installée hors Play Store ne peut pas recevoir l'accès aux notifications tant que l'utilisateur n'a pas touché « Autoriser les paramètres restreints » (Infos de l'appli → ⋮). Le texte de la carte Musique le dit.
- **Logo** : le dessin de l'icône adaptative est réduit à 86 % et descendu de 3 (moyeu du cadran à 57, juste sous le milieu ; descendu de 7, l'auteur le trouvait trop bas) pour respirer dans tous les masques ; le logo de l'accueil est affiché plus grand (174 dp) pour compenser. Vérifier un changement de logo par un rendu (Playwright) dans un masque rond et un carré arrondi.
- **Compose, ligne titre + étiquette** : dans une `Row`, un long titre prend toute la largeur et l'étiquette d'à côté se replie lettre par lettre (bug de « Mises à jour automatiques » dans l'accueil). Titre en `Modifier.weight(1f, fill = false)`, étiquette `maxLines = 1, softWrap = false`.
- Tests de géométrie : toujours vérifier sur **plusieurs graines de bruit** (voir `MapMatcherTest`), une seule graine cache les vrais problèmes.
- **Canvas : services morts ou payants** (testés le 28/10/2026) : Paxsenix demande désormais une clé (401 `key_required`), plusieurs déploiements Vercel de `spotify-canvas-api` ont disparu (`DEPLOYMENT_NOT_FOUND`) ou répondent 500 ; l'API publique d'Odesli (song.link, titre → id Spotify) répond 401 `PUBLIC_API_ACCESS_DEPRECATED`. Les autres projets exigent un cookie `sp_dc` d'un compte connecté : jamais dans Zenith.
- **`AndroidView` n'appelle sa fabrique qu'une fois** : pour une nouvelle vidéo, `CanvasVideo` est sous `key(file)`, sinon l'ancienne `TextureView` resterait branchée sur un lecteur libéré.
- **Ouvrir le lecteur depuis Zenith (Android 14+)** : le `PendingIntent` de la session est créé par le lecteur, en arrière-plan ; il faut `setPendingIntentBackgroundActivityStartMode` pour qu'il démarre avec le droit de Zenith (au premier plan). Repli : `getLaunchIntentForPackage`, qui exige les `<queries>` du manifeste (visibilité des paquets).

## API Lufop (format relevé dans un client open source, somansch/lufop_radar)

- `GET https://api.lufop.net/api?key=K&format=json&pays=FR&nbr=200&q=LAT,LON&m=M`, où `m` = rayon en km × 10.
- Plan gratuit : 200 requêtes/jour, 200 résultats par appel, **10 requêtes/minute**, FR/BE/CH, pas de `since=`.
- Réponse : liste d'objets (`name`, `lat`, `lng`, `vitesse`, `azimut`, `flash`, `update` « AAAA-MM-JJ hh:mm:ss », `voie`, `commune`) ; `null` quand la zone est vide ; un objet `{message}` en cas d'erreur. **Pas de champ `id`** en pratique : `harvest_lufop.py` identifie un radar par `lat,lng` (5 décimales).
- `pays=FR` renvoie aussi les radars espagnols et italiens proches de la frontière (noms « Radar Fixe ES 120 »…). Ils sont gardés.
- Premier passage réel (27/10/2026) : 150 requêtes → 3 135 radars ; quadrillage 413 zones → 425 après découpage des zones saturées.
- Le type se déduit du `name`, le plus précis d'abord : « Feu Rouge », « Passage Niveau » (passage à niveau, sans limite ; c'était un « radar fixe » avant le 28/10/2026), « Chantier », « Mobile », « Troncon Debut » / « Troncon Fin », « Discriminant », sinon fixe ; « Covoiturage » sans vitesse = à ignorer. Aucun nom « Mobile » dans la base au 28/10/2026.
- `azimut` (degrés, rempli pour environ 43 % des radars) et `flash` (`D`, `B`, `F`, ou vide ; probablement dos / les deux / face) ne sont **pas documentés** : on n'en tire pas encore de sens de circulation (un sens faux ferait rater l'alerte). À valider en comparant avec les radars OSM qui ont une relation `enforcement` avant de s'en servir.

## Données : règles

- Toutes les sources sont bienvenues. Chacune garde sa trace dans le champ `src` du radar (`gouv`, `sr`, `osm`, `lufop`, combinées par `+`).
- Fusion : regroupement à 80 m, puis `absorb_twins` : un radar OSM ou Lufop de la même famille (FIXED et DISCRIMINANT ensemble) à moins de 150 m d'un radar gardé, sens non opposés, est fondu dedans (sources ajoutées, limite officielle gardée) ; un radar fixe à moins de 30 m d'une caméra de tronçon est cette caméra. Les officiels ne sont jamais retirés. Au 28/10/2026 : 253 doublons fondus, paires à limites contradictoires 63 → 2. Limites hors 5–130 ignorées partout (radars et tuiles). La liste officielle fait foi pour la position, le type et la limite ; la carte Sécurité routière (`https://radars.securite-routiere.gouv.fr/radars/all?_format=json`, mêmes ids que data.gouv) ajoute ses radars plus récents, les longueurs de tronçon (détail `radars/<id>?_format=json`, `radartronconkm`) et les itinéraires ; OSM apporte le sens et les tronçons ; Lufop ajoute ce qui manque et confirme.
- Carte Sécurité routière : détails demandés seulement pour les tronçons et les radars absents de data.gouv (une centaine), 0,3 s entre deux, gardés 30 jours dans `official.json`. `radardirection` est un texte (« Paris vers Lille ») : pas encore exploité.
- Ne jamais deviner une limitation à l'aveugle : une route sans tag reste sans limite plutôt que d'afficher un 80 faux dans un village. Les limites déduites (`src` 2) s'affichent avec un anneau gris.
- **La base Lufop n'est jamais publiée en clair** (dépôt public : la redistribuer pourrait faire couper la clé). Toujours passer par `pipeline/lufop_db.sh`. Une base présente sur la release doit se relire, sinon le job échoue : jamais de redémarrage silencieux à zéro.
- Le quota Lufop ne doit jamais être dépassé : la base garde l'heure de chaque appel des dernières 24 h (`calls`), jamais plus de 150 sur une fenêtre de 24 h (donc sur un jour), quel que soit le nombre de passages. Chaque passage planifié prend une part aléatoire (30 à 60), pauses aléatoires de 6,5 à 15 s (10/min max), arrêt à la première erreur. Un appel compte dès qu'il part.
- La base Lufop est sauvegardée **juste après la récolte**, avant la fusion : le quota du jour est dépensé, rien ne doit le faire perdre.
- `build_radars.py check` refuse de publier un `radars.json` qui perd plus de 10 % des radars (comparé à l'ancienne version passée elle aussi par `absorb_twins`) ou 20 % d'un type de plus de 200 radars ; le résumé du job donne les comptes par source, par type et les noms Lufop.
